# 任务级基表扩列开关设计

## 目标

在创建模糊测试任务时提供任务级“扩展基表列”开关。默认关闭时，每张内置基表只保留当前 42 个核心列；开启时，每张表按可复现种子扩展到 200～500 列。任务运行期间不写入或归档任务级 SQL 文件，同一个“生成器版本 + 种子”在后续项目升级后仍必须生成字节级一致的基表 SQL。

## 非目标

- 不恢复扩列提交以前的固定核心列类型参数或每表 1000～2000 行数据。
- 不改变 79 张表的表类型、分区组合、索引、外键、临时表生命周期和每表 10～100 行种子数据等现有行为。
- 不对用户提供的任意自定义 DDL 自动增加扩展列。
- 不持久化每个任务生成的完整基表 SQL。

## 用户体验

“新建任务”表单增加以下控件：

- `扩展基表列（每表 200～500 列）`：默认关闭。
- `复现种子`：仅在开关开启时显示，使用十进制字符串输入；留空时由后端生成无符号 64 位随机种子。
- `生成器版本`：仅在开关开启时显示，首版为 `v1`，默认选择当前版本。

任务创建后，这三个值不可修改。任务卡片显示：

- 核心模式：`基表模式：核心列（42 列）`。
- 扩展模式：`基表模式：扩展列（200～500 列） · v1 · 种子 12345`。
- 扩展模式提供复制按钮，复制完整复现标识 `v1:12345`。

即使基表生成、连接或初始化失败，任务卡片也必须保留并显示最终模式、生成器版本和种子。

## API 契约

创建任务请求和任务响应增加三个字段：

- `expand_base_table_columns: bool`
- `base_table_seed: string | null`
- `base_table_generator_version: string | null`

种子始终使用字符串传输，避免 JavaScript 对大于 `2^53 - 1` 的整数丢失精度。

参数规则：

- 开关关闭时，种子和版本必须为空；响应中的两个字段均为 `null`。
- 开关开启时，版本留空则使用当前版本 `v1`；种子留空则由后端使用加密安全随机源生成 `[0, 2^64 - 1]` 范围内的十进制字符串。
- 种子必须是规范的无符号十进制整数，不允许符号、空白、小数或超出无符号 64 位范围。
- 关闭开关却传入种子或版本、非法种子、未知版本均由 API 返回 `422` 和中文错误说明。

## 架构与组件

新增 `select_fuzz/base_tables/` 包：

- `models.py`：定义不可变的 `BaseSqlBundle`，保存有序 `BaseSqlFile`、模式、生成器版本和种子。
- `loader.py`：把现有 `base_sql_dir` 一次性加载成内存包，并在连接数据库前解析、校验至少一张可用基表。
- `registry.py`：登记当前及历史生成器版本，负责规范化请求并分派版本实现。
- `v1.py`：冻结 `v1` 的扩列随机派生算法和输出格式。

现有 `tools/generate_sql_base_tables.py` 继续作为离线入口，但调用同一版本化生成能力。默认生成核心模式；显式传入扩列、版本和种子参数时生成扩展模式。仓库中的 `sql_base_tables/` 重新生成成核心模式，作为默认关闭状态的静态基线。

`FuzzTask` 支持直接接收 `BaseSqlBundle`。启动、附加 worker 初始化、临时表重建、worker 重连和 lost connection 恢复全部复用同一份不可变内存 SQL，不再反复读取目录。为兼容现有直接使用方式，仍允许只传 `base_sql_dir`；此时任务在连接数据库之前加载并缓存一次。

## 运行流程

1. API 校验并规范化开关、版本和种子。
2. 后端先创建带最终模式、版本和种子的任务快照。
3. 核心模式从配置的 `base_sql_dir` 加载内存包；扩展模式仅允许基于项目内置基表，由版本注册表在内存生成。
4. 后端解析和校验内存包。任何错误都在启动跳板机、建立数据库连接或执行 `DROP DATABASE` 之前转为“准备基表失败”。
5. 校验通过后创建 `FuzzTask`，所有 worker 使用同一个内存包。
6. 暂停任务时继续保留内存包；停止、失败或其他终态时释放 SQL 内容，只保留任务快照中的模式、版本和种子。

不创建任务级临时目录，也不把生成 SQL 写入 `artifacts/`、日志或其他持久化位置。

## `v1` 的跨版本复现契约

严格复现凭据为 `生成器版本 + 种子`。`v1` 冻结以下内容：

- 79 张核心表定义及顺序；
- 扩展列的命名、候选类型及候选顺序；
- 每张表目标列数的范围和计算方式；
- 类型参数、列值表达式和 SQL 渲染格式；
- 文件顺序和种子 SQL 格式。

任务种子只影响扩展列数量、类型、参数和扩展列种子值；核心列、核心列类型参数、核心种子值、表结构类别、索引和分区不受任务种子影响。

所有需要随机选择的 `v1` 值使用项目内固定的 SHA-256 派生函数。派生输入包含固定命名空间、版本、规范化种子、表编号、扩展列编号和用途标签；从摘要中按明确字节序取整数并映射到候选范围。`v1` 不以 Python `random.choice()`、`shuffle()` 或解释器内部状态作为兼容契约。

后续需要改变算法或输出时必须新增 `v2`，不得修改 `v1` 的输出。项目长期保留旧版实现和兼容性金标测试，前端可继续选择已登记的旧版本。

## 自定义基表

核心模式继续支持任意现有 `base_sql_dir`。扩展算法只适用于项目内置的 79 张基表。如果服务配置了非内置目录又请求扩展模式，任务在连接数据库前以中文错误进入“准备基表失败”，不得静默忽略开关或改用另一套表。

## 日志与可观测性

任务快照始终包含扩展开关、最终版本和最终种子。运行 SQL 的 JSONL 日志增加同样的基表元信息，便于从错误 SQL 定位复现凭据，但不记录完整基表 SQL。关闭模式只记录核心模式，版本和种子为空。

## 错误处理

- 请求字段冲突、非法种子和未知版本：HTTP `422`。
- 生成器异常、生成结果无法解析、缺表、列数或扩展列校验失败：任务状态为“失败”，阶段为“准备基表”，且不连接目标数据库。
- 自定义目录请求扩展模式：同样在“准备基表”阶段失败且不连接数据库。
- 初始化 SQL 执行失败：沿用现有失败和连接清理流程，卡片仍显示复现信息。

## 测试与验收

- 默认请求关闭扩列；静态 79 张表均为 42 个核心列且不存在 `extra_tN_NNN` 列。
- 开启后 79 张表均为 200～500 列，插入列和值一一对应。
- 同一 `v1 + 种子` 在重复生成、并发生成和新进程中得到完全一致的字节序列。
- 不同种子至少改变扩展结构；任务种子不改变核心列定义。
- 为代表性种子保存完整 bundle SHA-256 金标，任何项目或 Python 升级不得改变 `v1` 金标。
- 两个不同种子的并发任务互不污染。
- worker 初始化、临时表重建、worker 重连和 lost connection 恢复均不重新读目录，也不重新生成结构。
- 在无效 bundle、自定义目录扩展等失败场景中，数据库 `connect()` 和所有 SQL 执行次数为零。
- API 覆盖默认值、自动种子、手动种子、边界值、非法组合和未知版本。
- 前端生产构建通过，并人工验证条件表单、任务卡片、失败状态和复制复现标识。
- 运行过程不生成任务级 SQL 文件。
- 现有后端全量测试、离线生成器校验和前端生产构建继续通过。
